## The findings

### Wachiman, on `9d35758`

1. **Fix, docs: ADR 0041 says shape and corner radius are never per section, but overrides carry
   both.** It cited the inspector's Corners slider, `webcam-edits.ts:100`, `webcam-model.ts:190`,
   `session.ts:383`, and two tests that already put `shape` on an override. Valid: ADR 0039 is
   proposed, not implemented, so the override format allows both today. Fixed in `1bcab52` by
   rewording the ADR.
2. **Consider, cleanup: `clampCameraCornerRadius` divides by a literal `100` instead of using the
   step.** Correct only while the step is 0.01. Fixed in `1bcab52`.

Both are claim-vs-code and coherence findings, the kind Pullfrog and CodeRabbit did not post.

### Pullfrog, on `9d35758`

3. **Changing shape does not re-snap a bubble placed by a preset.** The stored centre was computed
   for the old box width. A 0.22 bubble at bottom-left on 1920×1080 moves about 30 px inward when
   it becomes a Rectangle, and no preset stays highlighted. Valid, functional, user-visible.
   Fixed in `1bcab52`, following Pullfrog's suggested approach.

Pullfrog's suggested approach was `WEBCAM_POSITION_PRESETS.find(...)` on the old centre, then
commit `{ shape, position }`. Both of CodeRabbit's next findings are in that code.

### CodeRabbit, on `1bcab52`: regressions in the fix

4. **Ambiguous preset: `find` picks the first of several presets that share a centre.**
   Recomputed from `webcamPresetCenter` at `1bcab52`: on a 1080×1920 (vertical) frame at size 0.49,
   a circle is 940.8 px wide; with the 76.8 px margin, `2 × (470.4 + 76.8) = 1094.4 ≥ 1080`, so
   every column returns x = 0.5. Bottom-left, bottom and bottom-right are the same point. A bubble
   at "bottom" matches bottom-left first. As a Rectangle (705.6 px wide) bottom-left is
   x = 429.6 / 1080 = 0.398, so the bubble jumps 0.102 × 1080 = **110 px left**. Reachable: the
   size slider goes to 0.6 and vertical export exists. Valid, an edge case. Fixed in `084f6f8`
   (re-snap only when exactly one preset matches).
5. **An override that inherits its position gets a copy of it.** Circle to Square keeps the width,
   so the recomputed centre equals the current one, but the fix still committed `position` into
   the override segment. From then on, moving the global position no longer moves that segment.
   Valid, data integrity, invisible until later. Fixed in `084f6f8` (commit `position` only when
   it moves).

### CodeRabbit, on `084f6f8`: outside the delta

6. **`webcamPresetCenter` sizes the box without `webcamRect`'s caps.** `webcamRect` caps the
   height at `frame.width / aspect` and `frame.height`; the preset centre did not. Recomputed: a
   0.6 circle on 1080×1920 would be 1152 px, rendered at 1080. Bottom presets put its centre at
   y = 1267.2 px, so the gap to the bottom edge is 112.8 px instead of 76.8 px. Valid, cosmetic.
   The author notes the gap predates the PR for circles; the rectangle does not hit the cap on
   today's export frames. Fixed in `c11f99d` with a test.

Neither Wachiman nor Pullfrog flagged it on `9d35758`, where the function was already changed.

## Why CodeRabbit found what the others did not

- **It reviewed the fix commit at all.** Wachiman never saw `1bcab52`. Pullfrog saw it and said
  the feedback was "addressed cleanly", reviewing its own suggestion.
- **The delta was small.** Four files, 38 changed lines (the ADR was excluded by its path filter). A small diff got the attention a
  42-file review spreads across everything.
- **It tested the new code at boundary inputs.** Both findings come from asking what `find` does
  when several presets coincide and what a no-op change writes. The 110 px figure shows it worked
  through concrete numbers (narrow frame, large size) rather than the typical case.
- **It read the function the fix calls.** Finding 6 is outside the delta's diff: it came from
  reading `webcamPresetCenter`, which the new inspector code calls, and comparing it with
  `webcamRect`.

CodeRabbit posted nothing on the first commit, so it was not the stronger reviewer of the
feature. It was the only one that checked the fixes.

## Why Wachiman did not compete after the first commit

- **The trigger.** kaipu-record's caller runs on `pull_request: [opened, ready_for_review]` and
  `issue_comment`. A push (`synchronize`) does not start a run. The template documents this
  ("A later push does not re-run it").
- **The engine already does incremental review.** `/wachi review` re-reviews the changes since the
  last reviewed commit (the `agent-review sha=` marker) and hands open threads with the owner's
  replies to the batch that holds their file. Nobody commented `/wachi review` on #475, so that
  path never ran.
- **Thread replies get no answer.** The review body says "Reply in a comment's thread to answer
  it". The author replied "Fixed in 1bcab524" on both threads at 21:20:38–40. An inline reply is a
  `pull_request_review_comment` event, which the caller does not subscribe to, and replies are only
  read during the next review run. Both threads are still open with no Wachiman reply. Pullfrog
  answered "Addressed in 1bcab52" 69 s after the reply; CodeRabbit verified each fix and resolved
  its threads.

## What this suggests

1. **Run on `synchronize`, incremental.** Three of six valid findings were on fix commits. This is
   improvement 4 of the [README](README.md); #475 moves it up. The engine part exists; the trigger
   and the concurrency rules do not (see the next point).
2. **Answer thread replies without a push.** Either subscribe to `pull_request_review_comment` with
   a thread-only mode, or stop promising an answer in the review body. Trap: the author's agent
   replies right after it pushes (13 s here). With the current per-PR concurrency group and
   `cancel-in-progress: true`, a reply-triggered run would cancel the push's review. Replies need
   their own group or a queue, and the trust gate (`OWNER`, `MEMBER`, `COLLABORATOR`) must run
   before any paid step.
3. **Check fixes for regressions.** In an incremental run, give the batch the findings the fix
   answers and ask it to test the new code at boundary inputs: coinciding values, no-op changes,
   size caps. Findings 4 and 5 are that shape. This is a prompt change on top of point 1.
4. **The flow questions still matter.** Wachiman missed the first-round functional bug (finding 3)
   that Pullfrog found by following "change shape" to its effect on the preset. That is the gap
   the [flow questions spec](../../specs/2026-10-31-flow-questions-and-evidence-design.md) targets.

**Replay to measure points 1 and 3:** add rows to a `bench.sh` manifest
([replay/](../replay/README.md)) with base `9d35758` and head `1bcab52` (then base `1bcab52`, head
`084f6f8`), run Wachiman three times with the effort fixed (the
[2026-11-01 replay](../2026-11-01/README.md) shows one run is not a measurement), and check
whether it reports findings 4, 5 and 6. Not done yet.
