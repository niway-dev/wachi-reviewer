# GPT-6.1 Sol critique of the risk-map and review-depth design (2026-10-31)

Verdict: keep the map as a way to find code; do not use it yet to decide which changes deserve depth. What is missing first is a required check of the full flow; indicators can help that question, they do not replace it.

## A. Does the map give what was missing?
Partly. Promising for #465, insufficient alone for #467. `Bun.Transpiler.scan()` returns imports and export names, not an AST with declarations, positions or resolved references; "modified symbol", "new call" or "value feeding a hash" need another extraction layer, and `git grep` output must be called a textual match. On #465 a search for `window.electronAPI.startFileDrag` finds the toast and, with context, `markCopySeen` before the drag: plausible win, and an import-only graph would miss it. On #467 the map points at `library-detail-page.tsx` and `runner.ready`, but the decisive question ("when the export ends, how does this screen that stays open learn about it?") still needs reading `use-local-library.ts`, `export-runner.ts` and `recording-hub.ts`. On #464 the pieces were already in one batch. On #466 counting references adds little to a remount/useRef question. On #463 finding `randomUUID` is easy; proving it lands in an identity that must survive mounts needs data-flow following. Noise: generic names, barrels, aliases, mocks, type imports, generated code, shared hooks. Build candidates with provenance and explicit limits, not a "complete impact map".

## B. Thresholds vs the model judging depth
The owner is right to reject uncalibrated risk thresholds; the engine must keep fixed operational limits. Cleanest split: (1) code gathers evidence; (2) the model judges which contract may break, what evidence is missing, whether it needs to investigate; (3) code authorises work: validates the request, applies budget, call count and pending coverage. The model may return `needs_investigation` with a concrete question, premises and candidate files; it never decides dollars, tools, agent count or recursive chains. "Code decides" means code governs execution. A budget cap alone is not enough: a finite, visible admission policy is needed, preserving base coverage.

## C. Automatic deep mode
Reasonable inside an explicit reserve; the trigger must never raise the total budget. Likely failure: everything looks risky and every review burns its maximum; or breadth and depth share money and later files go unreviewed. Inverse failure: poor indicators call #465 trivial. Separate a coverage amount and an investigation amount; what does not fit stays as a pending contract with its reason. Start in observation mode: log requests and measure their usefulness before enabling extra calls.

## D. `contracts` and the three dispositions
Transferring questions between batches is cross-batch coordination. Better than summaries only if each item carries: originating action and location, concrete hypothesis, premises with code references, missing evidence, status and responsible batch; and the receiver reads code and can refute it. Dispositions: investigate now (code is in the repo); transfer once with an explicit owner; ask the author only when product intent or external information is missing. Do not auto-publish every open contract as `question`; do not accept "closed" because two citations were attached (the engine checks format and existence of references, not that they prove the conclusion). Remaining hole: a contract no batch formulated never enters the queue.

## E. Traditional tools and five cheap indicators
Separate detecting a problem, estimating severity and prioritising where to look. SonarQube (impact × likelihood per rule; hotspots need review), CodeQL (`@precision` vs `@problem.severity` as separate axes), Semgrep and ESLint (configured severity is reporting policy), change-impact analysis (candidate impact set, not proof), churn/hotspots (Microsoft relative churn; CodeScene), CRAP (needs real coverage), Google 2011 bug prediction (recency-weighted fix commits as a reviewer hint). Five cheap indicators, not yet summed into a score: (1) candidate consumers of the changed export, split production/types/tests; (2) new connections to existing code incl. qualified members and literal IPC/event channels, with their other uses; (3) relative churn of the change; (4) change frequency and recency with a bounded window and the history size available; (5) historical co-change: files that usually change with this one and were left out. 1–2 find missing evidence; 3–5 prioritise search. In shallow clones, missing history is unknown, not zero risk.

## F. Harness
Claude can read a precomputed file: `runProvider` enables Read/Glob/Grep and passes auxiliary dirs via `--add-dir` (engine.ts ~1603, claude-code.ts ~160), as for `pr.json` and `threads.json`. No new permission is needed to read unchanged files; the prompt already asks for callers. Pullfrog's `opencode: V1` and `agent: claude` labels do not prove the observed review ran on OpenCode, nor that the harness caused the quality difference. Migrating is a separate evaluation. The adapter has no `--max-turns`; the only visible limit is monetary, so "higher turn cap" is not a knob that exists today.

## G. Multi-language and ADR 0002
Keep Bun for JS/TS and an explicit textual fallback elsewhere, with a common evidence format carrying provenance (`module_scan`, `text_match`, `history`) and status (`complete`, `truncated`, `unsupported`, `failed`). A Rust/Go binary, a WASM parser or vendored code are third-party code either way; they do not preserve ADR 0002's purpose by avoiding `node_modules`. Reopen only when representative PRs in demanded languages show retrieval-attributable misses that a concrete parser reduces at acceptable cost: a new condition, not one of the current ones.

## H. ADR compatibility
Core fits ADR 0001 (local map, read tools, engine posts, controlled budget) as long as a model request never raises limits; changing review questions touches decision 4 (policy versioned apart), still incomplete. ADR 0002: installing a mapper contradicts it. ADR 0006 is proposed, not accepted-and-implemented; head content is evidence under review, never authority to lower severity, exclude files or change budgets. `readBaseInstructions` already reads from base; ADR 0006's status note lags that part.

## I. Build first, falsify cheapest
First: the flow-contract check inside the existing batch (what changes, equivalent path, how visible state updates, what happens on leave-and-return), with evidence and open questions. Then minimal precedent retrieval (qualified calls, hooks). Postpone the aggregate score, the cross-batch queue and automatic depth. Cheapest experiment: ablation on the affected batches of #465 and #467 at their original heads: current prompt; prompt + contract questions; prompt + map; both. Same model and limits, several repetitions, map built by generic rules with no bug names. Record: precedent retrieved, causal chain completed, correct finding, false alarms, cost. Distinguishes "the map does not retrieve the evidence" from "it retrieves it and the model still does not ask". Two cases can overfit: approval needs new PRs and clean controls; keeping the 17 needs the full five-PR replay.

## Five changes, ranked
1. Make the flow check part of breadth, not gated on a high-risk trigger.
2. Reduce the initial map to verifiable candidates incl. qualified calls; drop the claim of semantic references from `scan()`.
3. Separate judgement from execution: the model requests investigation; the engine keeps coverage, budget and a finite number of calls.
4. Turn `contracts` into refutable questions with an owner; no auto-publishing of everything pending, no closure by mere citations.
5. Validate with the ablation before adding thresholds, dependencies or a harness migration.
